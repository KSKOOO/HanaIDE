# Superpowers 开发方法论

一套完整的、高质量的软件开发和问题解决框架。包含从构思到完成的完整流程。

## 核心原则

1. **用户指令优先**：用户明确指令 > Superpowers 技能 > 默认系统行为
2. **先设计后实现**：不经过设计阶段绝不写任何代码
3. **测试先行**：没有失败的测试绝不写实现代码
4. **证据优于断言**：在声称成功之前必须运行验证
5. **根因分析**：修复前必须找到根本原因
6. **技能优先**：有 1% 可能性适用某个技能，就必须调用它

## 技能触发流程

```
用户消息 → 技能检查（即使 1% 可能）→ 调用技能 → 执行 → 响应
```

**警惕这些想法（意味着你在合理化跳过技能检查）：**
- "这只是个简单问题" — 问题都是任务，都要检查
- "我需要先了解更多上下文" — 技能检查在澄清问题之前
- "让我先探索代码库" — 技能告诉你如何探索，先检查
- "这不需要正式技能" — 有技能就用
- "我知道这意味着什么" — 知道概念 ≠ 使用技能

# 第一阶段：头脑风暴 (brainstorming)

## 何时使用

开始任何创造性工作时 —— 创建功能、构建组件、添加功能、或修改行为。

## 铁律

**在呈现设计并获得用户批准之前，不得调用任何实现技能、编写任何代码、搭建任何项目、或采取任何实现动作。**

即使是"简单"项目也必须经过此流程。简单项目设计可以很短，但不能跳过。

## 检查清单

按顺序完成每个任务：

1. **探索项目上下文** — 检查文件、文档、最近提交
2. **提供可视化伴侣**（如果涉及视觉问题）— 单独消息，不与澄清问题合并
3. **提出澄清问题** — 一次一个，理解目的/约束/成功标准
4. **提出 2-3 种方案** — 包含权衡和你的建议
5. **呈现设计** — 按复杂度缩放各部分，每部分后获批准
6. **编写设计文档** — 保存到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` 并提交
7. **设计自检** — 快速检查占位符、矛盾、歧义、范围
8. **用户审查书面规范** — 请求用户在继续前审查规范文件
9. **过渡到实现** — 调用 writing-plans 技能创建实施计划

## 流程图

```
探索项目上下文 → 视觉问题？ → 是 → 提供可视化伴侣
                            ↓否
                    提出澄清问题
                            ↓
                    提出 2-3 种方案
                            ↓
                    呈现设计部分
                            ↓
                    用户批准设计？ → 否 → 修订并重新呈现
                            ↓是
                    编写设计文档
                            ↓
                    设计自检（内联修复）
                            ↓
                    用户审查规范？ → 是 → 调用 writing-plans
                            ↓否
                    返回修订
```

## 理解想法

- 先检查项目当前状态（文件、文档、最近提交）
- 一次问一个问题
- 尽可能用多选题
- 聚焦于理解：目的、约束、成功标准

## 探索方案

- 提出 2-3 种不同方案，包含权衡
- 对话式呈现，包含建议和理由
- 领先推荐方案并解释原因

## 呈现设计

- 相信理解后呈现设计
- 按复杂度缩放各部分：简单几句话，复杂 200-300 字
- 每部分后询问是否正确
- 涵盖：架构、组件、数据流、错误处理、测试

## 设计隔离原则

- 将系统分解为更小的单元，每个单元有明确的单一目的
- 通过良好定义的接口通信
- 可以独立理解和测试
- 能够回答：这个单元做什么？如何使用？依赖什么？

## 设计自检

编写规范文档后，用新眼光审视：

1. **占位符扫描**：有"TBD"、"TODO"、不完整部分、或模糊需求吗？修复它们。
2. **内部一致性**：各部分矛盾吗？架构与功能描述匹配吗？
3. **范围检查**：是否足够聚焦于单一实施计划？还是需要分解？
4. **歧义检查**：任何需求可以被两种不同方式解释吗？

内联修复任何问题。

## 关键原则

- **一次一问** — 不要用多个问题压倒
- **多选首选** — 比开放式更容易回答
- **YAGNI 严格** — 从所有设计中移除不必要的功能
- **探索替代方案** — 总是提出 2-3 种方案再确定
- **增量验证** — 呈现设计，获得批准后再推进
- **保持灵活** — 事情不合理时回去澄清

# 第二阶段：编写计划 (writing-plans)

## 何时使用

有了规范或需求，需要为多步骤任务编写实施计划时。

## 概述

编写全面实施计划，假设工程师对代码库零上下文且品味可疑。记录他们需要知道的一切：每个任务要触碰的文件、代码、测试、可能需要检查的文档、如何测试。给出完整计划作为小口小口的任务。DRY。YAGNI。TDD。频繁提交。

**开始时宣布：** "我正在使用 writing-plans 技能创建实施计划。"

**计划保存到：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`

## 范围检查

如果规范涵盖多个独立子系统，应该在头脑风暴期间已分解为子项目规范。如果没有，建议分解为单独计划——每个子系统一个。

## 文件结构

定义任务前，先映射哪些文件将被创建或修改，以及每个文件的职责：
- 设计边界清晰、接口定义明确的单元
- 每个文件应该有一个清晰的职责
- 一起变化的文件应该放一起
- 在现有代码库中，遵循既定模式

## 小口任务粒度

**每步是一个动作（2-5 分钟）：**
- "写失败测试" — 一步
- "运行它确保失败" — 一步
- "写最小代码让测试通过" — 一步
- "运行测试确保通过" — 一步
- "提交" — 一步

## 计划文档头部

**每个计划必须以此头部开始：**

```markdown
# [功能名称] 实施计划

> **面向代理工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐任务实施此计划。步骤使用复选框（`- [ ]`）语法跟踪。

**目标：** [一句话描述构建内容]

**架构：** [2-3 句关于方法的内容]

**技术栈：** [关键技术和库]

---
```

## 任务结构

```markdown
### 任务 N：[组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

- [ ] **步骤 1：写失败测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试验证失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL，显示"function not defined"

- [ ] **步骤 3：写最小实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试验证通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
```

## 无占位符

每步必须包含工程师需要的实际内容。这些是**计划失败**——绝不写：
- "TBD"、"TODO"、"later"、"fill in details"
- "Add appropriate error handling" / "add validation" / "handle edge cases"
- "Write tests for the above"（无实际测试代码）
- "Similar to Task N"（重复代码——工程师可能乱序阅读任务）
- 描述做什么而不展示如何做（代码步骤需要代码块）
- 引用未在任何任务中定义的类型、函数或方法

## 自检

写完完整计划后，用新眼光审视规范，检查计划：

1. **规范覆盖：** 略读规范的每个部分/需求。能在计划中指向实现它的任务吗？列出任何空白。

2. **占位符扫描：** 在计划中搜索危险信号——上面"无占位符"部分的任何模式。修复它们。

3. **类型一致性：** 后期任务使用的类型、方法签名和属性名与早期任务定义的一致吗？

发现问题就内联修复。如果发现规范需求没有任务，添加任务。

## 执行交接

保存计划后，提供执行选择：

**"计划已完成并保存到 `docs/superpowers/plans/.md`。两种执行选项：**

**1. 子代理驱动（推荐）** — 我按任务派发新子代理，任务间审查，快速迭代

**2. 内联执行** — 在此会话中使用 executing-plans 执行任务，带检查点**

**选择哪个？"**

# 第三阶段：执行计划

## 方式一：子代理驱动开发 (subagent-driven-development)

## 何时使用

有实施计划，任务基本独立，要在当前会话中执行时。

**核心原则：** 每任务新子代理 + 两阶段审查（规范合规优先，然后代码质量）= 高质量、快迭代

## 为什么用子代理

委托任务给专门代理，隔离上下文。通过精确制作指令和上下文，确保它们专注并成功完成任务。子代理不应继承你的会话上下文或历史——你构建它们需要的确切内容。这也保留你自己的上下文用于协调工作。

## 流程

```
读取计划，提取所有任务完整文本，注意上下文，创建 TodoWrite

对每个任务：
  1. 派发实施者子代理
  2. 实施者问问题？→ 回答问题，提供上下文
  3. 实施者实施、测试、提交、自我审查
  4. 派发规范审查子代理
  5. 规范审查确认代码符合规范？→ 实施者修复规范差距
  6. 派发代码质量审查子代理
  7. 代码质量审查批准？→ 实施者修复质量问题
  8. 在 TodoWrite 中标记任务完成

所有任务完成后：
  派发最终代码审查子代理审查整个实现
  使用 superpowers:finishing-a-development-branch
```

## 处理实施者状态

实施者子代理报告四种状态之一。相应处理：

- **DONE：** 进入规范合规审查
- **DONE_WITH_CONCERNS：** 阅读担忧再继续。如果担忧关于正确性或范围，先解决
- **NEEDS_CONTEXT：** 实施者需要未提供的信息。提供缺失上下文并重新派发
- **BLOCKED：** 实施者无法完成任务。评估阻塞：
  1. 上下文问题 → 提供更多上下文，用相同模型重新派发
  2. 任务需要更多推理 → 用更有能力的模型重新派发
  3. 任务太大 → 分解为更小部分
  4. 计划本身错误 → 升级给人类

## 模型选择

使用最弱能处理每个角色的模型以节省成本和提高速度：

- **机械实现任务**（隔离函数、清晰规范、1-2 文件）：使用快速、便宜的模型
- **集成和判断任务**（多文件协调、模式匹配、调试）：使用标准模型
- **架构、设计和审查任务**：使用最有能力的可用模型

## 红旗

**绝不：**
- 在主/主分支开始实现（无用户明确同意）
- 跳过审查（规范合规或代码质量）
- 带未修复问题继续
- 并行派发多个实施子代理
- 让子代理读取计划文件（提供完整文本）
- 跳过场景设置上下文
- 忽略子代理问题
- 接受"差不多"的规范合规
- 跳过审查循环
- 让实施者自我审查取代实际审查
- **在规范合规批准之前开始代码质量审查**（顺序错误）
- 在任一审查有未解决问题时移到下一任务

## 方式二：执行计划 (executing-plans)

## 何时使用

有书面实施计划，要在单独会话中执行，带审查检查点时。

**注意：** 告诉人类合作伙伴，Superpowers 在有子代理访问时效果更好。如果没有子代理，使用 subagent-driven-development。

## 流程

### 步骤 1：加载和审查计划
1. 读取计划文件
2. 批判性审查 — 识别对计划的任何疑问或担忧
3. 如果有担忧：在开始前向人类合作伙伴提出
4. 如果没问题：创建 TodoWrite 并继续

### 步骤 2：执行任务

对每个任务：
1. 标记为进行中
2. 精确遵循每步（计划有小口步骤）
3. 按指定运行验证
4. 标记为完成

### 步骤 3：完成开发

所有任务完成并验证后：
- 宣布："我正在使用 finishing-a-development-branch 技能完成此工作"
- 必需子技能：superpowers:finishing-a-development-branch

## 何时停止寻求帮助

**遇到以下情况立即停止执行：**
- 遇到阻塞（缺少依赖、测试失败、指令不清晰）
- 计划有阻止开始的严重空白
- 不理解指令
- 验证反复失败

**宁可澄清不要猜测。**

## 何时回顾早期步骤

**返回审查（步骤 1）当：**
- 合作伙伴根据你的反馈更新计划
- 基本方法需要重新思考

**不要强行穿过阻塞** — 停止并提问。

# 第四阶段：测试驱动开发 (test-driven-development)

## 何时使用

实现任何功能或错误修复时，在写实现代码之前。

## 铁律

```
没有失败测试就不写生产代码
```

写代码前测试？删除它。从头开始。

## 红绿重构循环

```
RED（写失败测试） → 验证失败正确 → GREEN（最小代码） → 验证全部通过 → REFACTOR（清理）
```

### RED - 写失败测试

写一个最小测试，显示应该发生什么：

```typescript
test('重试失败操作 3 次', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```

**要求：**
- 一个行为
- 清晰名称
- 真实代码（除非不可避免否则不用 mock）

### 验证 RED - 看它失败

**必需。绝不跳过。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试失败（不是错误）
- 失败消息是预期的
- 因为功能缺失而失败（不是拼写错误）

**测试通过？** 你在测试现有行为。修复测试。

**测试错误？** 修复错误，重新运行直到正确失败。

### GREEN - 最小代码

写通过测试的最简单代码：

```typescript
async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i === 2) throw e;
    }
  }
  throw new Error('unreachable');
}
```

不要添加功能、重构其他代码、或在测试之外"改进"。

### 验证 GREEN - 看它通过

**必需。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试通过
- 其他测试仍通过
- 输出干净（无错误、警告）

**测试失败？** 修复代码，不是测试。

**其他测试失败？** 现在修复。

### REFACTOR - 清理

只有在绿色之后：
- 移除重复
- 改进名称
- 提取辅助函数

保持测试绿色。不要添加行为。

### 重复

下一个失败测试对应下一个功能。

## 好测试

| 质量 | 好 | 坏 |
|------|-----|-----|
| **最小** | 一件事。名称中有"and"？拆开它。 | `test('validates email and domain and whitespace')` |
| **清晰** | 名称描述行为 | `test('test1')` |
| **展示意图** | 展示期望的 API | 掩盖代码应该做什么 |

## 为什么顺序重要

**"我稍后写测试来验证它工作"**

代码后写的测试立即通过。立即通过什么都证明不了：
- 可能测试了错误的东西
- 可能测试实现，不是行为
- 可能遗漏你忘记的边界情况
- 你从未看到它 catch bug

测试优先迫使你看到测试失败，证明它实际测试了什么东西。

## 常见合理化

| 借口 | 现实 |
|------|------|
| "太简单不需要测试" | 简单代码也会坏。测试只需要 30 秒。 |
| "我稍后测试" | 立即通过的测试什么都证明不了。 |
| "之后测试达到同样目标" | 之后测试 = "这做什么？" 测试优先 = "这应该做什么？" |
| "我已经手动测试了" | 临时 ≠ 系统化。无记录，无法重运行。 |
| "删除 X 小时工作是浪费" | 沉没成本谬误。保留不可信的代码是技术债务。 |

## 红旗 - 停止并重新开始

- 代码在测试之前
- 测试在实现之后
- 测试立即通过
- 无法解释为什么测试失败
- "稍后"添加的测试
- 合理化"就这一次"
- "我已经手动测试了"
- "之后测试达到同样目的"
- "保持作为参考"或"adapt existing code"
- "已经花了 X 小时，删除是浪费"
- "TDD 是教条，我更务实"
- "这个不同因为..."

**所有这些意味着：删除代码。用 TDD 重新开始。**

# 第五阶段：系统调试 (systematic-debugging)

## 何时使用

遇到任何 bug、测试失败、或意外行为时，在提出修复之前。

## 铁律

```
未经根因调查不修复
```

如果未完成阶段 1，不能提出任何修复。

## 四阶段流程

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **一致地复现**
   - 能可靠地触发它吗？
   - 确切步骤是什么？
   - 每次都发生吗？
   - 如果不可复现 → 收集更多数据，不要猜测

3. **检查最近变更**
   - 什么变更可能导致这个？
   - Git diff、最近提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复之前，为每个组件边界添加诊断工具：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每层状态

   运行一次收集证据，显示在哪里断裂
   然后分析证据识别失败的组件
   然后调查那个特定组件
   ```

5. **追踪数据流**

   **当错误在调用栈深处时：**
   - 坏值从哪里来？
   - 什么调用时传入坏值？
   - 继续追踪直到找到源头
   - 在源头修复，不是症状

### 阶段 2：模式分析

**修复前找到模式：**

1. **找到工作示例**
   - 在同一代码库中找类似工作的代码
   - 什么类似工作的东西坏了？

2. **与参考对比**
   - 如果实现模式，完整阅读参考实现
   - 不要略读 — 读每一行
   - 在应用之前完全理解模式

3. **识别差异**
   - 工作的和坏的区别是什么？
   - 列出每个差异，无论多小
   - 不要假设"那不重要"

4. **理解依赖**
   - 这个还需要什么其他组件？
   - 什么设置、配置、环境？
   - 它做什么假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清楚陈述："我认为 X 是根因因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小测试**
   - 做最小可能变更来测试假设
   - 一次一个变量
   - 不要一次修复多个东西

3. **验证后再继续**
   - 成功？→ 阶段 4
   - 失败？→ 形成新假设
   - 不要在顶部添加更多修复

4. **当不知道时**
   - 说"I don't understand X"
   - 不要假装知道
   - 寻求帮助
   - 更多研究

### 阶段 4：实现

**修复根因，不是症状：**

1. **创建失败测试用例**
   - 最简单的复现
   - 可能的话自动化测试
   - 无框架时一次性测试脚本
   - 修复前必须有
   - 使用 `superpowers:test-driven-development` 技能写适当的失败测试

2. **实现单一修复**
   - 解决已识别的根因
   - 一次一个变更
   - 没有"既然在这里"的改进
   - 没有捆绑重构

3. **验证修复**
   - 测试现在通过？
   - 其他测试损坏？
   - 问题实际解决？

4. **如果修复不工作**
   - 停止
   - 计数：你尝试了多少修复？
   - 如果 < 3：返回阶段 1，用新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见阶段 4.5）**
   - 不要再尝试修复 4 而不讨论架构

5. **如果 3+ 修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每个修复在不同地方揭示新的共享状态/耦合/问题
   - 修复需要"大规模重构"来实现
   - 每个修复在其他地方产生新症状

   **停止并质疑基础：**
   - 这个模式根本上合理吗？
   - 我们是"纯粹靠惯性坚持"？
   - 应该重构架构 vs. 继续修复症状？

   **在尝试更多修复之前与人类合作伙伴讨论**

## 红旗 - 停止并遵循流程

如果发现自己想：
- "先快速修复，稍后调查"
- "试试改 X 看是否有效"
- "添加多个变更，运行测试"
- "跳过测试，我会手动验证"
- "大概是 X，让我修那个"
- "我不完全理解但这可能有效"
- "模式说 X 但我会不同地适应"
- "主要问题如下：[列出修复不调查]"
- 在追踪数据流之前提出解决方案
- **"再试一次修复"（已经尝试 2+ 次）**
- **每个修复在不同地方揭示新问题**

**所有这些意味着：停止。返回阶段 1。**

# 第六阶段：代码审查

## 请求代码审查 (requesting-code-review)

## 何时请求审查

**必需：**
- 子代理驱动开发中的每个任务之后
- 主要功能完成后
- 合并到主分支之前

**可选但有价值：**
- 卡住时（新视角）
- 重构前（基线检查）
- 修复复杂 bug 后

## 如何请求

1. **获取 git SHA：**
   ```bash
   BASE_SHA=$(git rev-parse HEAD~1)  # 或 origin/main
   HEAD_SHA=$(git rev-parse HEAD)
   ```

2. **派发代码审查子代理：**

   使用 Task 工具与 `general-purpose` 类型，填充模板：
   - `{DESCRIPTION}` - 你构建了什么
   - `{PLAN_OR_REQUIREMENTS}` - 应该做什么
   - `{BASE_SHA}` - 起始提交
   - `{HEAD_SHA}` - 结束提交

3. **处理反馈：**
   - 立即修复关键问题
   - 重要问题在继续前修复
   - 次要问题记录供稍后
   - 如果审查者错了（带推理）反驳

## 接收代码审查 (receiving-code-review)

## 何时使用

接收代码审查反馈时，在实现建议之前，特别是如果反馈不清晰或技术上有问题时。

## 响应模式

```
接收代码审查反馈时：

1. 阅读：完成反馈不反应
2. 理解：用自己话重述需求（或提问）
3. 验证：对照代码库现实检查
4. 评估：对这个代码库在技术上是合理的？
5. 响应：技术确认或有理有据的反驳
6. 实现：一次一个，测试每个
```

## 禁止的响应

**绝不：**
- "You're absolutely right!"（明确违反 CLAUDE.md）
- "Great point!" / "Excellent feedback!"（表演性）
- "Let me implement that now"（验证之前）

**替代：**
- 重述技术需求
- 提问澄清
- 如果错误，用技术推理反驳
- 直接开始工作（行动 > 言语）

## 处理不清晰反馈

```
如果任何项目不清晰：
  停止 — 还不实现任何东西
  对不清晰项目提问

原因：项目可能相关。部分理解 = 错误实现。
```

## 何时反驳

反驳当：
- 建议破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用功能）
- 对这个技术栈在技术上不正确
- 存在遗留/兼容性原因
- 与人类合作伙伴的架构决策冲突

**如何反驳：**
- 使用技术推理，不是防御性
- 问具体问题
- 引用工作的测试/代码
- 如果是架构的，牵扯人类合作伙伴

## 确认正确反馈

当反馈**是**正确的：
```
✅ "Fixed. [简要描述变更]"
✅ "Good catch - [具体问题]。Fixed in [位置]。"
✅ [直接修复并在代码中展示]
```

# 第七阶段：完成开发分支 (finishing-a-development-branch)

## 何时使用

实现完成，所有测试通过，需要决定如何集成工作时。

## 流程

### 步骤 1：验证测试

**在呈现选项前，验证测试通过：**

```bash
npm test / cargo test / pytest / go test ./...
```

**如果测试失败：**
```
Tests failing (<N> failures). Must fix before completing:

[Show failures]

Cannot proceed with merge/PR until tests pass.
```

停止。不要进入步骤 2。

### 步骤 2：检测环境

**在呈现选项前确定工作区状态：**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
```

| 状态 | 菜单 | 清理 |
|------|------|------|
| `GIT_DIR == GIT_COMMON`（正常仓库） | 标准 4 选项 | 无工作树需清理 |
| `GIT_DIR != GIT_COMMON`，命名分支 | 标准 4 选项 | 按来源清理 |
| `GIT_DIR != GIT_COMMON`，游离 HEAD | 减少 3 选项（无合并） | 无清理（外部管理） |

### 步骤 3：呈现选项

**正常仓库和命名分支工作树 — 呈现这 4 个选项：**

```
Implementation complete. What would you like to do?

1. Merge back to <base-branch> locally
2. Push and create a Pull Request
3. Keep the branch as-is (I'll handle it later)
4. Discard this work

Which option?
```

### 步骤 4：执行选择

#### 选项 1：本地合并

```bash
# 获取主仓库根目录以确保安全
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# 先合并 — 确认成功再删除任何东西
git checkout <base-branch>
git pull
git merge <feature-branch>

# 验证合并结果上的测试
<test command>

# 仅在合并成功后：清理工作树，删除分支
git branch -d <feature-branch>
```

#### 选项 2：推送并创建 PR

```bash
# 推送分支
git push -u origin <feature-branch>

# 创建 PR
gh pr create --title "<title>" --body "$(cat <<'EOF'
## Summary
<2-3 bullets of what changed>

## Test Plan
- [ ] <verification steps>
EOF
)"
```

**不要清理工作树** — 用户需要它来迭代 PR 反馈。

#### 选项 3：保持原样

报告：`"Keeping branch <name>. Worktree preserved at <path>."`

#### 选项 4：丢弃

**先确认：**
```
This will permanently delete:
- Branch <name>
- All commits: <commit-list>
- Worktree at <path>

Type 'discard' to confirm.
```

# 第八阶段：完成前验证 (verification-before-completion)

## 铁律

```
无新鲜验证证据不声称完成
```

如果在此消息中未运行验证命令，不能声称它通过。

## 门控函数

```
在声称任何状态或表达满意之前：

1. 识别：什么命令证明此声称？
2. 运行：执行完整命令（新鲜的、完整的）
3. 读取：完整输出，检查退出码，计数失败
4. 验证：输出确认声称？
   - 如果否：用具证据陈述实际状态
   - 如果是：用具证据陈述声称
5. 仅那时：做出声称

跳过任何步骤 = 撒谎，不是验证
```

## 常见声称

| 声称 | 需要 | 不充分 |
|------|------|--------|
| Tests pass | 测试命令输出：0 failures | 上次运行，"应该通过" |
| Linter clean | Linter 输出：0 errors | 部分检查，推测 |
| Build succeeds | Build 命令：exit 0 | Linter 通过，日志看起来好 |
| Bug fixed | 测试原始症状：通过 | 代码变更，假设修复 |
| Regression test works | 红绿循环验证 | 测试通过一次 |

## 红旗 - 停止

- 使用"should"、"probably"、"seems to"
- 在验证前表达满意（"Great!"、"Perfect!"、"Done!"等）
- 在未验证时即将提交/推送/PR
- 信任代理成功报告
- 依赖部分验证
- 认为"就这一次"
- 累且想要工作完成
- **任何暗示成功而无运行验证的措辞**

# 使用 Git 工作树 (using-git-worktrees)

## 何时使用

开始需要与当前工作区隔离的功能工作时，或在执行实施计划之前 —— 确保存在隔离工作区。

## 概述

确保工作在隔离工作区中进行。优先使用平台原生工作树工具。仅在无原生工具时回退到手动 git worktree。

**开始时宣布：** "我正在使用 using-git-worktrees 技能设置隔离工作区。"

## 步骤 0：检测现有隔离

**在创建任何东西之前，检查是否已在隔离工作区中。**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

**子模块守卫：** `GIT_DIR != GIT_COMMON` 在 git 子模块内也为真。在得出"已在工作树中"之前，验证不是子模块：

```bash
git rev-parse --show-superproject-working-tree 2>/dev/null
```

**如果 `GIT_DIR != GIT_COMMON`（且不是子模块）：** 已在链接工作树中。跳到项目设置。不要创建另一个工作树。

## 步骤 1：创建隔离工作区

**你有两个机制。按此顺序尝试。**

### 1a. 原生工作树工具（首选）

用户要求隔离工作区。有创建工作树的方式吗？可能是一个名为 `EnterWorktree`、`WorktreeCreate` 的工具、`/worktree` 命令、或 `--worktree` 标志。如果有，使用它并跳到步骤 3。

原生工具自动处理目录放置、分支创建和清理。

### 1b. Git Worktree 回退

**仅当步骤 1a 不适用时使用** — 无原生工作树工具可用。手动创建工作树。

#### 目录选择

按此优先级顺序。明确用户偏好始终优先于观察到的文件系统状态。

1. **检查指令中的声明工作树目录偏好。** 如果用户已指定，使用它不提问。

2. **检查现有项目本地工作树目录：**
   ```bash
   ls -d .worktrees 2>/dev/null     # 首选（隐藏）
   ls -d worktrees 2>/dev/null      # 替代
   ```
   如果找到，使用它。

3. **如果无其他指导**，默认为项目根目录的 `.worktrees/`。

## 步骤 3：项目设置

自动检测并运行适当设置：

```bash
# Node.js
if [ -f package.json ]; then npm install; fi

# Rust
if [ -f Cargo.toml ]; then cargo build; fi

# Python
if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
if [ -f pyproject.toml ]; then poetry install; fi

# Go
if [ -f go.mod ]; then go mod download; fi
```

## 步骤 4：验证干净基线

运行测试确保工作区开始干净：

```bash
npm test / cargo test / pytest / go test ./...
```

**如果测试失败：** 报告失败，询问是否继续或调查。

**如果测试通过：** 报告就绪。

# 第九阶段：编写技能 (writing-skills)

## 何时使用

创建新技能、编辑现有技能、或在部署前验证技能是否正常工作。

## 概述

**编写技能就是测试驱动开发（TDD）应用于流程文档。**

**核心原则：** 如果你没有看到没有技能的代理失败，你就不知道这个技能是否教会了正确的东西。

## 什么是技能

**技能**是一个经过验证的技术、模式或工具的参考指南。技能帮助未来的 Claude 实例找到并应用有效方法。

**技能是：** 可重用技术、模式、工具、参考指南

**技能不是：** 关于你如何一次解决问题的叙事

## TDD 映射

| TDD 概念 | 技能创建 |
|-------------|----------------|
| **测试用例** | 带子代理的压力场景 |
| **生产代码** | 技能文档（SKILL.md） |
| **测试失败（RED）** | 无技能时代理违反规则（基线） |
| **测试通过（GREEN）** | 有技能时代理遵守 |
| **重构** | 在保持合规的同时堵住漏洞 |

整个技能创建过程遵循 RED-GREEN-REFACTOR。

## 创建技能的时机

**创建当：**
- 这个技术对你来说不是凭直觉就显而易见的
- 你会在跨项目中参考这个
- 模式适用范围广（不是项目特定的）
- 其他人也会受益

**不要为以下创建：**
- 一次性解决方案
- 其他地方有充分文档记录的标准实践
- 项目特定的约定（放在 CLAUDE.md）
- 机械约束（如果是可正则/验证强制的，用自动化——把文档留给判断）

## 技能类型

### 技术
带步骤要遵循的具体方法（条件等待、根因追踪）

### 模式
思考问题的方式（使用标志扁平化、测试不变量）

### 参考
API 文档、语法指南、工具文档

## 目录结构

```
skills/
  skill-name/
    SKILL.md              # 主要参考（必需）
    supporting-file.*     # 仅当需要时
```

**扁平命名空间** - 所有技能在一个可搜索命名空间

## SKILL.md 结构

**Frontmatter（YAML）：**
- 两个必需字段：`name` 和 `description`
- 最大 1024 字符
- `name`：仅使用字母、数字和连字符
- `description`：第三人称，仅描述何时使用（不是做什么）

```markdown
---
name: Skill-Name-With-Hyphens
description: Use when [specific triggering conditions and symptoms]
---

# Skill Name

## Overview
这是什么？1-2 句话的核心原则。

## When to Use
触发症状和使用情况列表
何时不使用

## Core Pattern
前后代码对比

## Quick Reference
常见操作的表格或要点

## Implementation
简单模式的内联代码
重参考的链接

## Common Mistakes
什么出错 + 修复
```

## 描述优化（CSO）

**关键目的：** 让未来的 Claude 能找到你的技能

### 描述字段的陷阱

```yaml
# ❌ 坏：总结工作流 - Claude 可能遵循这个而不是读完整技能
description: Use when executing plans - dispatches subagent per task with code review between tasks

# ✅ 好：仅触发条件，无工作流总结
description: Use when executing implementation plans with independent tasks in the current session
```

### 内容要求
- 使用具体触发词、症状和情况
- 描述*问题*（竞态条件、不一致行为）而非*语言特定症状*
- 保持触发词技术无关（除非技能本身是技术特定的）
- 第三人称书写
- **绝不总结技能的工作流**

## 编写技能检查清单

**RED 阶段 - 写失败测试：**
- [ ] 创建压力场景（3+ 组合压力用于纪律技能）
- [ ] 无技能运行场景 - 记录基线行为
- [ ] 识别合理化/失败中的模式

**GREEN 阶段 - 写最小技能：**
- [ ] 名称仅使用字母、数字、连字符
- [ ] YAML frontmatter 有必需字段
- [ ] 描述以 "Use when..." 开头
- [ ] 解决 RED 阶段识别的具体基线失败
- [ ] 运行场景有技能 - 验证代理现在遵守

**REFACTOR 阶段 - 堵住漏洞：**
- [ ] 从测试识别新的合理化
- [ ] 添加明确计数器（如纪律技能）
- [ ] 从所有测试迭代构建合理化表
- [ ] 创建红旗列表
- [ ] 重新测试直到无懈可击

## 铁律

```
无失败测试不写技能
```

适用于新技能和编辑现有技能。

# 第十阶段：派发并行代理 (dispatching-parallel-agents)

## 何时使用

面对 2+ 个独立任务，它们可以在没有共享状态或顺序依赖的情况下工作时。

## 概述

你委托任务给专门的代理，隔离上下文。通过精确制作它们的指令和上下文，确保它们专注并成功完成任务。

当有多个不相关的失败（不同的测试文件、不同的子系统、不同的 bug）时，顺序调查是浪费时间。每个调查是独立的，可以并行发生。

**核心原则：** 每个独立问题域派发一个代理。让它们同时工作。

## 何时使用

**使用当：**
- 3+ 个测试文件失败，根因不同
- 多个子系统独立损坏
- 每个问题可以在不需要其他上下文的情况下理解
- 调查之间无共享状态

**不使用当：**
- 失败相关（修复一个可能修复其他）
- 需要理解完整系统状态
- 代理会相互干扰

## 模式

### 1. 识别独立域

按损坏内容分组失败：
- 文件 A 测试：工具批准流程
- 文件 B 测试：批处理完成行为
- 文件 C 测试：中止功能

每个域是独立的 - 修复工具批准不影响中止测试。

### 2. 创建聚焦代理任务

每个代理获取：
- **特定范围：** 一个测试文件或子系统
- **明确目标：** 让这些测试通过
- **约束：** 不要更改其他代码
- **期望输出：** 你发现和修复了什么

### 3. 并行派发

```
Agent 1 → 修复 src/agents/agent-tool-abort.test.ts
Agent 2 → 修复 src/agents/batch-completion-behavior.test.ts
Agent 3 → 修复 src/agents/tool-approval-race-conditions.test.ts
# 三个同时运行
```

### 4. 审查和集成

代理返回时：
- 阅读每个摘要
- 验证修复不冲突
- 运行完整测试套件
- 集成所有变更

## 代理提示结构

好的代理提示是：
1. **聚焦** - 一个清晰的问题域
2. **自包含** - 理解问题所需的所有上下文
3. **输出具体** - 代理应该返回什么？

```markdown
修复 src/agents/agent-tool-abort.test.ts 中 3 个失败的测试：

1. "should abort tool with partial output capture" - 期望消息中有 'interrupted at'
2. "should handle mixed completed and aborted tools" - 快速工具中止而非完成
3. "should properly track pendingToolCount" - 期望 3 个结果但得到 0

这些是时序/竞态条件问题。你的任务：

1. 读取测试文件，理解每个测试验证什么
2. 识别根因 - 时序问题还是实际 bug？
3. 修复：
   - 用基于事件的等待替换任意超时
   - 如果发现 bug 修复中止实现
   - 如果测试更改行为则调整测试期望

不要只是增加超时 - 找到真正问题。

返回：你发现和修复了什么摘要。
```

## 常见错误

**❌ 太宽泛：** "修复所有测试" - 代理迷路
**✅ 具体：** "修复 agent-tool-abort.test.ts" - 聚焦范围

**❌ 无上下文：** "修复竞态条件" - 代理不知道在哪里
**✅ 有上下文：** 粘贴错误消息和测试名称

**❌ 无约束：** 代理可能重构一切
**✅ 有约束：** "不要更改生产代码" 或 "仅修复测试"

## 关键好处

1. **并行化** - 多个调查同时发生
2. **聚焦** - 每个代理范围窄，需要跟踪的上下文更少
3. **独立性** - 代理不会相互干扰
4. **速度** - 3 个问题用 1 个问题的时间解决

# 快速参考

## 技能优先级

当多个技能可能适用时，使用此顺序：

1. **流程技能优先**（头脑风暴、调试）— 这些决定如何处理任务
2. **实现技能第二**（前端设计、mcp-builder）— 这些指导执行

## 技能类型

- **刚性**（TDD、调试）：精确遵循。不要适应掉纪律。
- **灵活**（模式）：根据上下文调整。

技能本身告诉你哪个。

## 工作流程摘要

```
头脑风暴 → 设计批准 → 编写计划 → 执行计划（子代理或手动）
                                      ↓
                              TDD 实现每个任务
                                      ↓
                              代码审查（每任务后）
                                      ↓
                              完成前验证
                                      ↓
                              完成开发分支
```

## 红线总结

**绝不：**
- 在设计批准前写代码
- 无失败测试写实现代码
- 无验证声称成功
- 不找根因就修复
- 在主分支直接工作（无用户同意）
- 跳过任何审查
- 带未修复问题继续

**始终：**
- 先设计后实现
- 测试先行
- 证据优于断言
- 先找根因再修复
- 使用隔离工作区
- 验证一切

# 中文代码审查 (chinese-code-review)

## 何时使用

进行代码审查（Code Review）时。适用于审查他人代码或接收审查反馈。

## 核心原则

代码审查需要技术评估，不是情感表演。

## 响应模式

```
接收代码审查反馈时：
1. 阅读：完成反馈不反应
2. 理解：用自己话重述需求（或提问）
3. 验证：对照代码库现实检查
4. 评估：对这个代码库在技术上是合理的？
5. 响应：技术确认或有理有据的反驳
6. 实现：一次一个，测试每个
```

## 审查清单

| 检查项 | 说明 |
|--------|------|
| 逻辑正确性 | 代码逻辑是否符合需求？ |
| 边界条件 | 空值、空列表、除零检查？ |
| 错误处理 | 异常捕获、资源释放？ |
| 性能 | 循环、查询优化？ |
| 安全 | 注入、XSS、权限？ |
| 可读性 | 命名、注释、结构？ |

## 禁止的响应

**绝不：**
- "你是对的！" / "好观点！"（表演性同意）
- "我来实现"（验证之前）

**替代：**
- 重述技术需求
- 提问澄清
- 如果错误，用技术推理反驳
- 直接开始工作

| type | 说明 |
|------|------|

| perf | 性能优化 |

```bash

git commit -m "feat(auth): add JWT refresh token support"

git commit -m "fixed stuff"
git commit -m "WIP"
git commit -m "update"
```
